# Dungeon migration to pure game MVU

Proposal, 12 November 2026, against Dungeon a17c941. This is the first consumer of the FP-RISC game MVU proposal. The change preserves the built-in level, control bindings and turn pacing.

1. **Characterize input and turns.** Record model observations for starting play, moving, interacting, using an inventory slot, restarting and quitting. Include rapid input across two ticks. Today step queues raw key codes and the tick advances play. Preserve that queue discipline when supplying decoded gameplay messages. [Game shell](../src/dungeon.fpr) · [Rules](../src/mods/dungeonrules.fpr)
2. **Introduce the game Msg type and pure handlers.** Map keyboard subscriptions to messages such as Move direction, Interact and UseSlot index. Both W and Up decode to the same move. Keep the existing key-driven rules entry as a temporary adapter for tests while moving rule dispatch to semantic actions. Have update return ordered Log commands for changed announcements and the existing win/death transcript. Emit Quit and CaptureFrame once from their respective transitions.
3. **Move boot into Game.run.** Supply window configuration, initial flags and pure callbacks. Compose the existing scene and UI into one layered element tree. Remove the capture flag from the view result when the runner supports post-render capture. Move endpoint acquisition, closure and shutdown logging into the adapter as appropriate.
4. **Accept the migration.** Run the existing pure rules suite. Add headless assertions for equivalent keyboard bindings, queued movement, one announcement on a changed message and one capture despite repeated renders. Use a scripted win or loss to check the final transcript. Run the existing Sol harness through the staged SDK and check title, play, movement, capture and clean exit. [Rules suite](../tests/rules.fpr) · [GUI harness](../tests/check.sol)

Completion means init, update, subs and view can all execute in a test process without opening a window, creating an actor or accessing a device.

## First computation task: the shared navigation field

Enemy turns already compute one breadth-first distance field from the player for all enemies. Extract that search into pure start/step functions carrying the frontier, visited distances and stable neighbour order. A step expands at most N cells. Submit a navigation job once per required enemy phase, using only the board dimensions, passability and player position. Keep the ordered enemy movement, collision checks, damage and end-of-turn processing in the original rules order.

While the field is pending, the shell can redraw and accept controls. Queue ordinary player actions until the enemy phase commits. Restart or level replacement cancels the old request. Deliver the matching result once and resume the turn at the original enemy-phase boundary. Differential tests compare the synchronous and chunked fields and complete turn outcomes, including ties, fleeing and multiple enemies reaching the player. Use an enlarged maze to measure responsiveness; the built-in level may be faster synchronously. [Current enemy phase](../src/mods/dungeonrules.fpr)
